# Phone Link (`nd.phone-audio`)

One QR code turns your phone — Android Chrome or iOS Safari — into a **wireless keyboard** (English / Khmer typing and voice dictation through the phone keyboard's mic) and a **low-latency speaker** for Windows playback audio (YouTube, games, browsers, music, Electron), over local Wi-Fi or USB tethering. No APK, App Store install, Bluetooth adapter, or external cloud server is required.

The desktop view has **Audio** and **Keyboard** tabs; the phone page served at the pairing URL has the same two tabs. Both share **one server, one port, one 6-digit pairing PIN, and one QR**. The pairing token is persisted on the PC (`userData/nd-phone-link/pairing.json`) and remembered by the phone browser, so the code stays valid across stop/start and app restarts — scan once, and only **New Code** rotates it.

## Architecture

- **Unified Pairing & Signaling Server (Main Process)**: `PhoneAudioService` hosts local-only HTTP + WebSocket (`ws`) bound per active non-virtual local IPv4 interface (`Wi-Fi`, `USB Tethering`, `Ethernet`, and `127.0.0.1`), protected by a persistent pairing token + 6-digit PIN with rate-limited pairing, `timingSafeEqual` checks, and local-subnet validation. WebSockets are routed by `?app=keyboard|audio` into independent single-client slots, so one phone can use both tabs at once.
- **Phone shell**: `/` serves a tabbed shell that pairs once with the PIN and embeds `/keyboard` and `/audio` as same-origin iframes. The Audio frame loads lazily on first visit and stays alive while the Keyboard tab is used, so playback continues while typing.
- **Keyboard injection**: Text and allowlisted keys from the phone are injected into the focused Windows app through the nd-core sidecar (`CoreInput.typeText` / `sendKey`) with a serialized queue. Fails closed when the sidecar is not running.
- **Capture (Windows)**: Electron `session.setDisplayMediaRequestHandler()` with Windows system audio loopback (`audio: 'loopback'` or `'loopbackWithMute'`) paired with `navigator.mediaDevices.getDisplayMedia()` in the desktop renderer, immediately stopping any video track so zero video frames are sent. Includes an optional virtual audio device fallback (e.g. VB-CABLE).
- **Media Transport (WebRTC)**: Direct peer-to-peer local WebRTC audio track preferring stereo Opus (`ptime=10`), measured RTT/jitter stats, and automatic reconnection on transient Wi-Fi drops. Signaling is relayed main ↔ desktop renderer ↔ phone.
- **Mobile Audio Receiver**: `/audio` respects Android Chrome and iOS Safari autoplay policies via explicit tap-to-play, registers Media Session metadata and play/pause/stop handlers for lock-screen controls, and re-negotiates the peer connection on `visibilitychange`/`pageshow`/`focus` so iOS lock/background suspension recovers automatically on return.
- **iOS limits**: Safari suspends web audio while the screen is locked or the tab is backgrounded (a WebKit platform limit, not a bug in this extension); playback resumes when the page returns to the foreground, or via the lock-screen play control / on-page resume button. True locked-screen playback would require a native iOS companion app.
